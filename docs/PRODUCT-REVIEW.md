# 知识库插件产品体验审计与优化计划

- 版本基线：dsh-kb v0.8.3（475 篇报告 / 8 分类 / 22 系列 / 94 篇 LLM Wiki / 284 个图谱节点 / 1120 条共现边）
- 审计时间：2026-11-18
- 审计方式：真实生产实例（127.0.0.1:8816，DSH 面板 iframe 内 + 直连页），Playwright 走查 + API 采样 + 键盘/移动/暗色测试；证据截图在 [`docs/review-shots/`](review-shots/)
- 审计身份：产品体验官视角（不是代码 review），关注「用户能不能看懂、找得到、敢用」

---

## 一、结论摘要

1. **能力面已经很强，短板集中在"可信度"和"状态反馈"**。检索、AI 问答、周报、图谱、Wiki、公开外链六条主线都跑通了，首屏 389ms、接口 36–52ms、全程 0 console error，工程完成度高于同类个人知识库。
2. **一个会直接摧毁信任的 P0 bug**：随便输入无意义关键词，界面显示「839 条结果」并把全库报告列出来（`20-search-flood.png`）。用户第一次搜不到东西时，得到的不是"没有结果"，而是"全库都相关"，搜索从此不可信。
3. **移动端有一个明显视觉事故**：侧栏导航在 390px 下逐字竖排断字（`16-mobile.png`），首屏只能看到 1.5 张卡片。
4. **长任务缺反馈**：AI 问答 15–20 秒只有一句"正在检索报告并组织答案…"，不能取消、没有进度；图谱画布首屏白屏 1.8 秒。
5. **无障碍基本盘不错**（186 个按钮均有可读名称，h1 唯一，skip-link 存在），但抽屉没有焦点陷阱——键盘用户按 Tab 会跑到侧栏，aria-modal 形同虚设。

## 三、问题清单（按优先级）

> 每条给：现象 → 证据 → 影响 → 建议 → 验收标准。工作量估算按 1 人日 ≈ 8h。

### P0（本周必须修，影响"敢不敢用"）

#### P0-1 搜索把"无词法命中"的报告也算成结果，垃圾词返回全库

- **现象**：输入 `zzz-no-such-keyword` → 界面显示「839 条结果」，列出 Minecraft 版本记录；输入 `资产负债率` → 824 条（词法只命中几篇，其余都是"语义相似"被扩进来）；切到「关键词」模式同一查询 → 0 条。
- **证据**：`20-search-flood.png`；API 直连 `q=zzz…` total=839、`mode=lexical` total=0。
- **根因**：`kb_store._article/_node_candidates` 与报告候选的规则是「无词法命中但余弦 ≥0.28 就保留」，而 bge-small-zh 对无关中文的余弦基线普遍在 0.3–0.5，阈值等于没设；同时 `total` 直接把全部候选数返回给 UI，被当成"相关结果数"。
- **影响**：搜索不可信；空态永远不出现；AI 问答的候选池同样被灌入噪声（ask 走 hybrid top-k）。
- **建议（按顺序）**：
  1. 查询词 ≥1 个中文词时，**词法命中是硬门槛**（标题/正文/摘要/标签/实体任一命中），语义只负责"排序"而不是"召回"；
  2. 真正的"语义模式"单独开关，改用自适应阈值：`cos ≥ max(0.45, μ + 1.2σ)` 且与 top1 的差距 < 0.12，并限制"最多 3×limit 条"；
  3. `total` 拆语义：`total_lexical`（精确数）+ `total_semantic`（估算），UI 上显示「N 篇包含关键词 · 另有 M 篇语义相关」；
  4. 加回归：`zzz…` 必须 0 条、空态文案出现；`铝业`、`资产负债率` 的 top5 必须含词法命中项；跑 `cli_eval` 保证 Recall@5 不下降。
- **验收**：`verify-app` 增加"垃圾词→空态"用例；上述 3 条查询手工验收；eval baseline 对比表进 PR。
- **估时**：0.5–1 人日（后端 0.5 + 前端计数/空态 0.3 + 测试 0.2）。

#### P0-2 移动端导航逐字竖排、首屏被挤压

- **现象**：390×844 下侧栏导航「未读 / 收藏 / 公开 / AI 问答 / 周报 / 知识图谱 / LLM Wiki」每个字单独一行，部分被裁切；分类标签区被压缩；工具栏高 155px，首屏只能看到 1.5 张卡。
- **证据**：`16-mobile.png`；CSS mobile 段 `.kb-navitem { flex: 1; justify-content: center; gap: 8px; }`——7 个等分项在 390px 里放不下，文字被迫逐字换行。
- **影响**：移动端基本不可用（很多用户就是手机随手看）。
- **建议**：移动端导航改**横向滚动**（`flex: 0 0 auto; white-space: nowrap; overflow-x: auto`，隐藏滚动条），主视图按钮加图标；「标签」区默认折叠进「更多筛选」；工具栏拆成「搜索行 + 一行动作」，默认首屏 ≥2 卡。
- **验收**：390px 与 360px 截图无竖排断字、无横向滚动、首屏卡数 ≥2；`verify-app` 加 `isElementOverflowing` 断言。
- **估时**：0.5 人日。

#### P0-3 图谱画布首屏 1.8 秒白屏

- **现象**：点「打开可视化画布」后约 1.8s 才出现节点；期间是空白背景，没有骨架/进度。
- **证据**：`14-canvas.png` 加载前白屏；Playwright 计时 1812ms。
- **根因**：320 次力导向迭代同步跑在主线程，先算完才渲染第一帧。
- **建议**：①首帧先渲染「圆形/随机初始布局 + 骨架文案」，布局放 `requestAnimationFrame` 分段算（每次 ≤8ms）或 Web Worker；②布局结果按 `(节点集合 hash)` 缓存在 sessionStorage，二次进入直接复用；③提供「稳定布局」开关。
- **验收**：首帧 < 300ms、可交互 < 1s；弱化动画 `prefers-reduced-motion` 下不跑。
- **估时**：0.5–1 人日。

### P1（两周内，影响"用得顺不顺"）

#### P1-1 抽屉无焦点陷阱，键盘/读屏用户体验断裂

- **现象**：打开抽屉后连按 10 次 Tab，焦点回到 `BODY`（跑到侧栏/工具栏），虽然 `role=dialog`、`aria-modal=true`、`aria-labelledby=kb-drawer-title`。
- **证据**：Playwright 焦点探测（start `kb-drawer-panel` → after 10 tabs `BODY`，`inDrawer:false`）。
- **建议**：焦点循环（Tab/Shift+Tab 在抽屉内首尾相接）、初始焦点给标题（`tabindex=-1`）、Esc 关闭后焦点归还触发卡片；补 `aria-describedby`（摘要）与「关闭」按钮的 `aria-keyshortcuts`。
- **验收**：Tab 30 次始终在抽屉内；axe 扫描无 critical；Esc 关闭后焦点回到原卡。
- **估时**：0.3 人日。

#### P1-2 AI 问答 15–20 秒无进度、不可取消

- **现象**：提交后只有一句「正在检索报告并组织答案…」，没有分步状态、没有取消、没有"通常需要 15–20 秒"的预期；用户容易以为卡死并重复提交。
- **建议**：①2 秒内先返回"已检索到 12 篇相关报告"和可点开的候选列表（检索本身 50ms）；②答案走流式（SSE 或轮询增量）逐字出现；③加「停止生成」按钮；④超时/失败给明确原因与重试。
- **验收**：首屏反馈 < 2s；取消生效 < 1s；完成后自动滚动到答案顶部；弱网下不清空输入。
- **估时**：1–1.5 人日。

#### P1-3 搜索态计数语义混乱

- **现象**：搜索时侧栏「全部 839」「全部分类 839」，分页「1–20 / 839」，但未读/收藏显示「—」；用户不知道 839 是"相关结果"还是"全库"。
- **建议**：搜索态把「全部」改名为「搜索结果」并加 tooltip；分类计数在搜索态隐藏或降级为「全库 N」；分页文案「第 1–20 条，共 839 条（含语义相关）」。
- **验收**：截图走查 + 文案评审通过。

#### P1-4 LLM Wiki 索引每张卡都挂「重新生成」（94 个按钮）

- **现象**：`/kb/wiki/` 94 张卡片，每张都有「重新生成」，视觉噪音大、误触成本高（每次生成要 10–20s、消耗额度）。
- **建议**：索引页只保留顶部「生成一篇」；单卡操作收进 hover 菜单 / 详情页；给卡片加"过期"徽章而不直接给按钮。
- **验收**：索引页按钮 ≤5 个；过期卡一眼可见。

## 四、能力缺口（相对产品北极星「用户只投喂，AI 组织」）

1. **投喂入口缺失**：目前写 reports/ 依赖 Hermes 或手工文件，插件内没有「上传/新建」入口，也没有"入库成功/去重"的反馈（`content_hash` 已有但只用于增量）。建议：拖拽上传 HTML/MD → 落到 reports/ → 触发 sync + AI 处理，并在页面顶部给"已入库，正在生成摘要"的进度条（分层用任务表）。
2. **人工覆盖缺失**：AI 分类/系列错了只能改 HTML 注释 `<!-- bl:category: X -->`，普通用户做不到。建议抽屉里给「改分类/系列」下拉 + 标记"人工设定"，同步保留 AI 原始值。
3. **图谱关系类型单一**：现在只有共现边；下一阶段做"因果/对比/演进"类型化边（GRAPH-WIKI.md 已列），并在画布上按类型着色/筛选。
4. **Wiki 更新不闭环**：新报告进来后旧文章会变 stale，但索引只标徽章，没有"批量重新生成过期文章"入口（后台每 180 秒才 1 篇）。
5. **公开能力偏裸**：无访问统计、无密码/过期链接、无 RSS；公开页也没有任何品牌/导航。
6. **通知缺失**：新报告入库、索引完成、文章过期，全程无提醒（DSH 内可发 toast/通知）。

## 五、优化计划（三个冲刺）

### Sprint A（P0，1–2 天）——「先让搜索可信、手机能看」

1. 搜索召回改造（P0-1）：词法硬门槛 + 语义排序 + total 拆分 + 空态回归。
2. 移动端导航修复（P0-2）：横向滚动 + 工具栏精简 + 折叠标签区。
3. 画布首帧优化（P0-3）：骨架 + 分段布局 + 布局缓存。
4. 回归：`pytest` / `verify-app` / `verify-dsh` 全绿；新增 3 条搜索用例。

**交付物**：修复 PR + 前后对比截图（搜索 flood vs 空态；390px 移动端；画布首帧计时）。

### Sprint B（P1，2–3 天）——「交互不再让人慌」

1. 抽屉焦点管理（P1-1）。
2. AI 问答进度/取消/流式（P1-2）。
3. 搜索态计数语义（P1-3）。
4. Wiki 索引按钮收敛（P1-4）。
5. 回归 + axe 自动扫描接入 `verify-app`。

### Sprint C（P2 + 能力，3–4 天）——「补齐投喂闭环」

1. P2-1 ~ P2-7 逐项。
2. 上传入口（与 Hermes 协作：文件落盘 + 触发 sync + 任务进度表）。
3. 人工覆盖分类/系列（前端下拉 + 后端 `set_classify(..., source="manual")`）。
4. 批量重新生成过期 wiki 文章（`POST /api/wiki/compile?stale=1`）。
5. 公开页增强 + RSS（可选）。

**不建议现在做**：图谱关系类型化引擎替换（成本高、收益待验证，先用现有共现边 + 人工覆盖）；向量库换 ANN（475 篇规模用 numpy 足够）。

## 七、值得保留的优点（不要在优化中弄丢）

- 首屏/接口快，列表扫描成本低（20 卡/页、分页清晰）。
- 分类 → 系列的两级结构与"未读/收藏/公开/AI 问答/周报/图谱/Wiki"的信息架构清楚。
- AI 摘要的来源可追溯（模型名、时间、引用上标），比"黑盒回答"可信。
- 空态、错误态文案已有中文与操作引导（"清空搜索/切换分类/清除日期"）。
- 无障碍基础好：按钮均有 aria-label、skip-link、focus 可见。
- 视觉（Neural Studio 风格）有辨识度，图谱交互（涟漪/脉冲）是差异化亮点，值得保留。
